# Аудит утечки и план устранения

**Дата:** 2026-10-19
**Итог:** утечка не «лёгкая и одинаковая для всех», а **доминирующая**. Она разная для разных
методов и полностью меняет выводы. При честном cutoff Recall@160 у co-visitation падает
с **0.1357 до 0.0214 (в 6.3 раза)**, у popular — с 0.0078 до 0.0048. Тезис README о том, что
co-visitation даёт «+271% над ALS», на текущих данных не подтверждён.

## Статус (2026-10-19)

Темпоральный сплит применён ко всем шагам (L1–L6 закрыты), репозиторий почищен (раздел 4). Результат честного прогона E1 (`--run synth`):

| Метод | С утечкой | Честно |
|---|---|---|
| Popular | 0.0078 | 0.0048 |
| ALS | 0.0368 | 0.0137 |
| Co-visitation | 0.1357 | 0.0216 |
| CatBoost ranker | 0.1613 | **0.0325** |
| Потолок retrieval (val) | 19.60% | 4.52% |

Открыто: L7, V2, V4–V6, E1b/E2/E3.

## 1. Что найдено

### Утечки (в порядке тяжести)

| # | Где | Что течёт | Доказательство |
|---|---|---|---|
| **L1** | `aggregate.py` → `build_matrix.py` → `train_als.py` → `generate_candidates_synth.py` | Synth-юзеры лежат в ALS-матрице вместе с событиями окна таргета. Их `user_factors` обучены **на самих таргет-парах** | 11 775 из 11 845 таргет-пар (**99.4%**) есть в `interactions_agg` с весом ≥5 (контакт). Оставшиеся 0.6% отрезаны лимитом top-100 |
| **L2** | `generate_candidates_covisit.py` (затравки) | 15 затравок = последние item из `interactions_agg`, то есть из окна таргета | **74%** затравок взяты из окна, **80% таргет-item сами стали затравками** |
| **L3** | `build_covisitation.py` (матрица) | Рёбра строятся в том числе по переходам юзера к его будущим таргетам | Абляция ниже: одна матрица без затравок держит 0.0319 против честных 0.0214 |
| **L4** | `build_features.py`: `item_popularity`, `item_n_users` | Считаются по данным с окном, то есть включают **собственный таргет-контакт юзера** (+1 юзер, +5 к весу). Для редких item это почти прямой флаг таргета | Это фичи №1 и №2 по importance (20.4 и 19.4) |
| **L5** | `build_features.py`: `user_top_vertical` | История берётся вместе с окном | — |
| **L6** | `build_item_pool.py`, `eval_popular_baseline.py`, `add_popular_fallback.py` | Пул и популярность считаются по данным с окном | popular: 0.0078 → 0.0048 |
| **L7** | `train_ranker.py` | `eval_set=val_pool` в CatBoost по умолчанию включает `use_best_model`: из 500 итераций выбрана 324-я **по тем же val-юзерам**, на которых потом считается Recall | `ranker.cbm`: 324 дерева, best_iteration=323 |

### Не утечки, но проблемы валидности

| # | Проблема | Последствие |
|---|---|---|
| **V1** | `prepare_local_eval.py` использует naive `datetime.fromisoformat(...).timestamp()` и берёт локальную зону (MSK). Фактический порог `local_eval.csv` — **2026-04-07 21:00 UTC** (`1775595600000`), а не 04-08 00:00 UTC | Проверено: 0 таргет-пар до 21:00 UTC и 76 пар до 00:00 UTC. Честный cutoff должен быть ровно `1775595600000` |
| **V2** | `local_eval.csv` построен только по `part_000` (все 7 131 юзер имеют `user_id % 100 == 0`). Фильтр «item ≥2 юзеров» посчитан на 1% юзеров | Распределение таргета отличается от официального. Бакеты сильно перекошены (h0=5445, v4=13) |
| **V3** | Synth-юзеры есть в train-матрице (берутся сохранённые `user_factors`), а официальные eval-юзеры — нет | Неактуально: прод-инференс из репозитория убран |
| **V4** | Нет novelty-фильтра: кандидаты включают уже виденные item, хотя таргет по определению новый | Covisit: 3 442 кандидата из истории до порога заранее не могут попасть в таргет и тратят слоты. Это улучшение, а не утечка, поэтому в абляции оно идёт отдельно |
| **V5** | 1 426 val-юзеров, без доверительных интервалов | На уровне ~0.02 разница в несколько тысячных может быть шумом |
| **V6** | `eval_recall.py`: covisit ранжируется внутри merged-таблицы, у ALS-only строк `covisit_score=0`, порядок при равенстве произвольный | Небольшой шум в строке «голый covisit» |

## 2. Измерения (уже выполнены)

Скрипт: `scripts/leak_check_covisit.py`. Повторяет логику `aggregate` / `build_covisitation` /
`build_item_pool` / `generate_candidates_covisit` / `eval_popular_baseline`, отличие только
в окне: `[THR − 28d, THR)`, `THR = 1775595600000`. Таргет и val-юзеры те же (1 426 юзеров из
`val_predictions.parquet`). Время работы ~10 мин.

| Вариант | Затравки | Матрица + пул | Recall@160 | Потолок@400 |
|---|---|---|---|---|
| Covisit, как в README (воспроизведение) | с утечкой | с утечкой | **0.1357** (в README 0.1364) | 0.158 |
| Covisit, только матрица честная | с утечкой | честные | 0.0746 | 0.093 |
| Covisit, только затравки честные | честные | с утечкой | 0.0319 | 0.031 |
| **Covisit честный** | честные | честные | **0.0214** | 0.022 |
| Popular, как в README | — | с утечкой | 0.0078 | — |
| **Popular честный** | — | честные | **0.0048** | — |

Выводы:
- Основная часть утечки covisit идёт через затравки (L2), но матрица (L3) тоже даёт заметный вклад.
- Утечка **неравномерная**: popular завышен в 1.6 раза, covisit в 6.3 раза. Сравнение методов
  на протечённых числах недействительно.
- ALS пока не измерен: нужно переобучение (~1 ч). По L1 ожидается сильное падение, потому что
  таргет-пары буквально лежат в строке юзера с весом 5.
- Честный потолок covisit-retrieval (2.2%) ниже, чем протечённый потолок ALS (7.6%). Значит,
  выбор архитектуры придётся пересматривать после честного прогона.

## 3. План: эксперименты (задача 1)

**Принцип:** меняется **только** cutoff данных. Таргет (`local_eval.csv`) не трогаем, val-сплит
фиксируем файлом, гиперпараметры остаются прежними. Тогда разница с E0 и есть величина утечки.

| ID | Что | Как | Стоимость |
|---|---|---|---|
| E0 | Протечённый пайплайн (текущие артефакты) | Перенести в `data/runs/leaky/`, переснять метрики одним `evaluate.py` | 5 мин |
| **E1** | Честный identical: L1–L6 закрыты | Весь пайплайн с `CUTOFF=1775595600000`: aggregate → matrix → ALS → covisit → pool → candidates → features → ranker → eval | ~3 ч (ALS ~1 ч, ранкер ~25 мин) |
| E1b | E1 + фикс L7 | Ранкер: `use_best_model=False` и фиксированные 500 итераций (или отдельный early-stop-сплит из train-юзеров) | +25 мин |
| E2 | Атрибуция по компонентам | Подставлять honest/leaky по одному: ALS, covisit-затравки, covisit-матрица (готово), фичи ранкера | ~1 ч поверх E1, артефакты переиспользуются |
| E3 | Fidelity (уже улучшения, не замер утечки) | V4: novelty-фильтр кандидатов. V2: перегенерировать `local_eval` по всем 100 партициям с UTC-порогом | отдельно, после E1 |

**Отчёт по каждому прогону:** Recall@160 (популярный, ALS, covisit, ранкер), потолок
retrieval, bootstrap 95% CI по юзерам (1000 ресэмплов), recall по бакетам. Результаты пишутся
в `data/runs/<run>/metrics.json`, сводная таблица собирается в `docs/experiments.md`.

**Защита от регрессии (автотесты, запускаются в каждом прогоне):**
1. `max(last_timestamp) < CUTOFF` во всех агрегатах.
2. Пересечение `local_eval` с историей synth-юзеров равно **0** (сейчас 11 775).
3. Ни одна covisit-затравка не имеет `timestamp ≥ CUTOFF`.

## 4. Сделано: чистка репозитория (задача 2)

- **Конфигурация.** `src/config.py`: два прогона, `synth` (cutoff `1775595600000`) и `leaky`
  (`1776211200000`), отличаются только cutoff. Все скрипты принимают `--run` и пишут в
  `data/runs/<run>/`. Прод-инференс из репозитория убран.

  eval (×2); popular-fallback перенесён в `merge_candidates.py`. Удалены `events_counter.py`,
